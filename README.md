# Advanced Java Backend (Email Service)

## Опис проєкту

Email Service - окремий мікросервіс, розроблений на Java з використанням Spring Boot, який забезпечує асинхронне надсилання електронних листів та відстеження статусів їх відправлення.

Сервіс інтегрується з мікросервісом Block2. Під час створення нового запису закупівлі (PurchaseRecord) Block2 формує повідомлення та надсилає його до RabbitMQ. 
Email Service отримує повідомлення з черги, зберігає його в Elasticsearch і виконує спробу відправлення через SMTP.

Якщо надсилання завершується помилкою, повідомлення отримує статус FAILED і зберігається для повторної обробки.

## Використані технології

- Java 17
- Spring Boot 3.3.0
- Spring AMQP (RabbitMQ)
- Spring Data Elasticsearch
- Spring Mail (JavaMailSender)

## Предметна область

Основною сутністю сервісу є EmailData, яка представляє електронний лист та інформацію про його відправлення.

Атрибути EmailData:

- id - унікальний ідентифікатор повідомлення.
- recipient - email-адреса отримувача.
- subject - тема листа.
- content - текст повідомлення.
- status - статус відправлення.
- errorMessage - інформація про помилку.
- attemptCount - кількість спроб відправлення.
- createdAt - час створення повідомлення. 
- lastAttemptAt - час останньої спроби.

### Статуси повідомлень

- `SENT` - повідомлення успішно передано SMTP-серверу.
- `FAILED` - під час відправлення виникла помилка.

У разі помилки зберігаються назва класу винятку та його повідомлення.

### Пагінація повідомлень

Для отримання списку повідомлень доступний endpoint:

GET /api/emails?page=0&size=20

Параметри:
- page - номер сторінки, починаючи з 0;
- size - кількість записів (від 1 до 100).

За замовчуванням: page=0, size=20.

Відповідь містить content, totalElements,
totalPages, number та size.

Якщо повідомлення за ID не знайдено,
повертається HTTP 404.

Некоректні параметри пагінації
повертають HTTP 400.

### Валідація

Перед збереженням перевіряється:
- наявність email отримувача;
- базова коректність формату email;
- непорожній subject;
- непорожній content.

### Обмеження повторних спроб

Параметр EMAIL_RETRY_MAX_ATTEMPTS визначає
максимальну кількість спроб надсилання.

0 - необмежена кількість спроб (за замовчуванням).

Додатне значення - максимальна кількість спроб,
включаючи початкове надсилання.

Після досягнення ліміту повідомлення
залишається зі статусом FAILED,
але більше не обробляється планувальником.

## Основна функціональність

### 1. Асинхронне отримання повідомлень

Для обміну повідомленнями використовується RabbitMQ.

Під час створення нового PurchaseRecord у Block2 формується повідомлення, що містить адресу отримувача, тему та текст електронного листа.

Повідомлення публікується в RabbitMQ та обробляється мікросервісом Block5 через EmailMessageListener.

Приклад повідомлення:

```json
{
  "recipient": "admin@example.com",
  "subject": "New purchase record",
  "content": "A new purchase record has been created."
}
```

### 2. Збереження повідомлень

Для збереження інформації про електронні листи використовується Elasticsearch.

Робота з базою даних здійснюється через EmailRepository, який використовує Spring Data Elasticsearch.

У базі зберігаються дані повідомлення, його статус, інформація про помилки та історія спроб відправлення у вигляді лічильника й часу останньої спроби.

### 3. Відправлення електронних листів

Надсилання здійснюється через SMTP за допомогою JavaMailSender.

Алгоритм роботи:

1. Отримання повідомлення з RabbitMQ.
2. Збереження інформації про повідомлення в Elasticsearch.
3. Виконання спроби відправлення через SMTP.
4. Оновлення статусу на SENT у разі успіху.
5. Оновлення статусу на FAILED та збереження errorMessage у разі помилки.


### 4. Повторне відправлення повідомлень

Для повторного надсилання використовується фонове завдання на основі Spring Scheduling.

Процедура запускається кожні 5 хвилин і виконує такі дії:

1. Отримує з Elasticsearch повідомлення зі статусом FAILED.
2. Повторно намагається відправити кожне повідомлення.
3. Збільшує attemptCount.
4. Оновлює lastAttemptAt.
5. У разі успіху встановлює статус SENT.
6. У разі помилки залишає статус FAILED та оновлює errorMessage.

Це дозволяє повторювати відправлення після тимчасової недоступності SMTP-сервера.

## Інтеграція з Block2

Block2 відповідає за роботу із сутностями PurchaseRecord та Material.

Під час успішного створення нового PurchaseRecord формується повідомлення про новий запис закупівлі.

Для передачі повідомлення використовується RabbitMQ.

Block5 отримує повідомлення асинхронно.

Таким чином, Block2 не виконує SMTP-відправлення самостійно, а передає цю відповідальність окремому мікросервісу.

## Налаштування

### Необхідне програмне забезпечення

Для запуску проєкту потрібні:

- JDK 17 або новіша сумісна версія
- Maven
- Docker Desktop із підтримкою Docker Compose
- Доступ до SMTP-сервера

### Змінні середовища

Параметри підключення до SMTP-сервера необхідно зберігати у файлі .env у корені проєкту.

Приклад налаштувань:

```bash
# RabbitMQ
RABBITMQ_USERNAME=rabbit
RABBITMQ_PASSWORD=secret

# SMTP
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=your-email@gmail.com
SMTP_PASSWORD=your-app-password
```

## Запуск через Docker Compose

Docker Compose використовується для запуску таких компонентів:

- RabbitMQ - брокер повідомлень.
- Elasticsearch - збереження даних електронних листів.
- Kibana - перегляд повідомлень та їхніх статусів.
- Email Service - мікросервіс надсилання листів.

### Налаштування 

Необхідно створити файл .env у корені проєкту та вказати параметри підключення до SMTP-сервера.

Збірка та запуск контейнерів

```bash
docker compose up -d --build
```

Перевірка контейнерів

```bash
docker compose ps
```

Перегляд логів

```bash
docker compose logs -f
```

Зупинка сервісів

```bash
docker compose down
```

## Тестування

### Збереження повідомлень під час недоступності Email Service

Для перевірки асинхронної взаємодії було виконано
тестування з тимчасово зупиненим Email Service.

Послідовність перевірки:

1. Запущено RabbitMQ та Block2.
2. Email Service залишено вимкненим.
3. Через Block2 створено новий PurchaseRecord.
4. Перевірено наявність повідомлення в черзі RabbitMQ.
5. Запущено Email Service.
6. Перевірено обробку повідомлення та надходження листа.

Результат: повідомлення, створене під час
недоступності Email Service, було оброблене
після його запуску.

### Відновлення після помилки SMTP

Для перевірки повторного відправлення було
тимчасово змінено SMTP_PORT на недоступний порт.

Після створення нового PurchaseRecord повідомлення
було збережене в Elasticsearch з такими даними:

- status: FAILED
- attemptCount: 1
- errorMessage: інформація про помилку підключення
- lastAttemptAt: час першої спроби

Після відновлення правильного SMTP_PORT
повідомлення було успішно відправлене.

Підсумковий стан того самого документа:

- status: SENT
- attemptCount: 2
- errorMessage: null
- lastAttemptAt: час повторної спроби

Це підтверджує роботу механізму повторного
надсилання повідомлень після тимчасової
недоступності SMTP-сервера.

### Модульні тести з Mockito

Перевіряються:

- збереження повідомлення перед відправленням;
- формування електронного листа;
- успішна відправка;
- обробка помилки SMTP;
- встановлення статусів SENT і FAILED;
- збереження errorMessage;
- збільшення attemptCount;
- оновлення lastAttemptAt;
- успішна та неуспішна повторна відправка;
- обробка декількох невідправлених повідомлень;
- валідація вхідних даних;
- поведінка при помилці збереження.

### Інтеграційні тести Elasticsearch

Для інтеграційного тестування використовується
Testcontainers, який запускає окремий контейнер
Elasticsearch.

Перевіряються:

- збереження повідомлення в реальній базі даних;
- отримання документа за ідентифікатором;
- пошук повідомлень зі статусом FAILED;
- оновлення статусу після повторної відправки;
- збереження інформації про помилки.

JavaMailSender у цих тестах замінюється mock-об'єктом,
тому реальні електронні листи не надсилаються.

### Тести RabbitMQ listener та scheduler

Перевіряються:

- передача отриманого повідомлення до EmailService;
- використання потрібної черги RabbitMQ;
- виклик процедури повторного відправлення;
- конфігурація інтервалу повторних спроб.

Ці тести перевіряють виклики та конфігурацію,
але не замінюють перевірку реального брокера.

## Запуск тестів

Для запуску всіх тестів необхідні:

- JDK 17;
- Maven;
- Docker Desktop;
- запущений Docker Engine.

Запуск тестів:

```bash
mvn clean test
```

Testcontainers самостійно створює та видаляє
тестовий контейнер Elasticsearch.

Робоча база даних для інтеграційних тестів не використовується.

## Перевірка через REST API

Email Service надає API для перегляду
збережених повідомлень.

Отримати список повідомлень:

```http
GET http://localhost:8085/api/emails
```

Отримати повідомлення за ідентифікатором:

```http
GET http://localhost:8085/api/emails/{id}
```

## Додаткова інформація

- RabbitMQ Management: http://localhost:15672
- Elasticsearch: http://localhost:9200
- Kibana: http://localhost:5601
- Email Service: http://localhost:8085
- Elasticsearch index: email-messages

Для перегляду повідомлень у Kibana необхідно
створити Data View для індексу email-messages
та відкрити розділ Discover.
